# Регулировщик — схема БД клиники (PostgreSQL)

Реляционная схема для приёма пациентов: пациенты, врачи, специальности, расписание (слоты), записи на приём, разграничение прав. Весь SQL проверен на живом PostgreSQL 16 — схема применяется без ошибок, защита от двойной записи и разграничение ролей подтверждены тестами.

## Файлы

- `init_schema.sql` — полный DDL: расширения, схема, ENUM, таблицы, ограничения, индексы, триггеры, функции, роли и права. Запускать под привилегированной ролью (она станет владельцем `SECURITY DEFINER`-функции записи).
- `init_data.sql` — примеры запросов по всем 6 сценариям + безопасная запись + настройка логин-учёток.

## 1. Архитектура (кратко)

Классическая нормализованная схема (3НФ) в отдельной схеме `clinic`. Ядро — четыре таблицы-сущности (`patients`, `doctors`, `specialties`, `slots`), одна связующая (`doctor_specialties`, M:N) и одна таблица событий (`appointments`).

Расписание моделируется как **дискретные слоты** (`slots`): у каждого врача заранее нарезаны интервалы приёма. Запись на приём — это привязка `appointments → slots`. Такой подход прямо ложится на задачу «найти ближайшее свободное окошко» и даёт естественную защиту от двойной записи через уникальность.

Безопасность записи держится на трёх слоях (все проверены под конкуренцией):
1. `SELECT … FOR UPDATE OF s SKIP LOCKED` — параллельные транзакции берут **разные** слоты, не блокируя друг друга;
2. частичный уникальный индекс `uq_appt_active_slot` — жёсткий барьер БД: на слот не более одной не-отменённой записи;
3. цикл с перехватом `unique_violation` в функции — на случай гонки в обход блокировки.

Разграничение прав — на уровне БД (`GRANT`/`REVOKE`). Запись бота идёт через `SECURITY DEFINER`-функцию, поэтому боту **не нужен** прямой INSERT в `appointments`.

## 2. Таблицы и связи

С интерактивной графической схемой БД можно ознакомиться [тут](https://dbdiagram.io/d/6a577f19c3a90dd98d41ae39).

```
specialties ─┬─< doctor_specialties >─┬─ doctors
             │                         │
             │                         └─< slots
             │                                │
             └─────────< appointments >───────┘
                              │
                        patients
```

| Таблица | Назначение | Ключевые связи |
|---|---|---|
| `specialties` | справочник специальностей | — |
| `doctors` | врачи (+ вычисляемое `full_name`, флаг `is_active`) | — |
| `doctor_specialties` | врач ↔ специальность (M:N) | FK → doctors, specialties |
| `patients` | пациенты | — |
| `slots` | слоты расписания врача | FK → doctors |
| `appointments` | записи на приём (событие) | FK → slots, patients, specialties |

Связи:
- `doctors` M:N `specialties` через `doctor_specialties`;
- `slots` N:1 `doctors`;
- `appointments` N:1 `slots`, N:1 `patients`, N:1 `specialties`.

`doctor_id` и время приёма у записи **не дублируются** — они выводятся через `slots` (нормализация). `specialty_id` на записи хранится осознанно: врач может иметь несколько специальностей, и важно знать, по какой из них шла запись.

## 3. Принятые решения и почему

- **Слот-ориентированное расписание.** Дискретные слоты вместо «окон доступности + вычисление на лету» — проще искать ближайшее свободное окошко и надёжнее защищаться от коллизий (уникальность на слот). Нарезку слотов делает утилита `generate_slots()`.
- **Защита от двойной записи через частичный уникальный индекс** `(slot_id) WHERE status <> 'cancelled'`, а не через флаг занятости на слоте. Плюсы: (а) остаётся нормализованным; (б) мягкая отмена автоматически освобождает слот (отменённые записи не считаются); (в) запись не требует UPDATE прав на `slots` — что идеально ложится на «бот не может менять расписание».
- **`FOR UPDATE … SKIP LOCKED`** для конкурентной записи: параллельные брони расходятся по разным слотам без взаимной блокировки (подтверждено: вторая транзакция отработала за ~0.03 c, пока первая держала блокировку).
- **`SECURITY DEFINER`-функция `book_nearest_slot`.** Бот получает только `EXECUTE`; вся логика записи (выбор слота, блокировка, вставка) выполняется под правами владельца. Это и безопаснее (бот не может делать произвольный INSERT), и точнее по правам. `created_by` пишется через `session_user`, поэтому в аудите остаётся реальный вызывающий, а не владелец функции.
- **`EXCLUDE USING gist`** на `slots` запрещает пересекающиеся слоты одного врача (сильнее, чем уникальность по времени старта).
- **Мягкая отмена.** Статусы `booked/cancelled/completed/no_show` (ENUM). Отмена — это `status='cancelled'` + `cancelled_at`; физического удаления нет. `CHECK` держит `cancelled_at` согласованным со статусом.
- **`updated_at` через общий триггер** `set_updated_at()` на всех таблицах — единообразный аудит.
- **«Уникально, если указано»** — частичные уникальные индексы `WHERE … IS NOT NULL` по паспорту, `telegram_id` и `lower(telegram_username)` (регистронезависимо). Они же обслуживают быстрый поиск (Index Scan).
- **Поиск врача по ФИО** — вычисляемый столбец `full_name` + GIN-индекс `gin_trgm_ops` под `ILIKE '%…%'`; однофамильцы возвращаются списком со специальностями.
- **Права через членство в групповых ролях.** `ai_bot_registrar/registrar/admin` — `NOLOGIN` группы; реальные учётки создаются отдельно и получают членство. `REVOKE … FROM PUBLIC` на схеме и функциях убирает неявные дефолтные права.
- **IDENTITY вместо SERIAL** — стандарт SQL, чище с точки зрения прав на последовательности.

## 5. Допущения

- **Только Russian / MVP-контекст**: справочник специальностей ведёт админ; коды специальностей латиницей (`gastroenterology`), отображаемые имена — на русском.
- **Специальность записи** доверяется функции: она выбирает слот врача, у которого эта специальность есть. Жёсткую БД-проверку «врач действительно имеет специальность записи» можно добавить триггером (см. расширения) — в MVP не критично.
- **Управление расписанием — за админом.** Если по процессу регистратор должен открывать/закрывать слоты, добавьте `GRANT INSERT, UPDATE ON clinic.slots TO registrar` (осознанно не выдано по принципу наименьших привилегий).
- **Часовой пояс**: слоты хранятся в `timestamptz`; нарезка `generate_slots` использует TZ сессии. Зафиксируйте TZ подключения (например `Europe/Moscow`).
- **Пароли логин-ролей** — из секрет-менеджера, не в SQL-файлах.

## 6. Возможные расширения

- **Шаблоны расписания** (`schedule_templates`: врач + день недели + рабочие часы) и авто-нарезка слотов из шаблона на N недель вперёд.
- **Триггер-валидация** соответствия `appointments.specialty_id` набору специальностей врача слота.
- **Приёмы/учреждения**: таблица `facilities` (ФАП → амбулатория → поликлиника → больница) и привязка врачей/слотов к узлу — под тиражирование на сеть.
- **Аудит-лог** изменений (`audit_log` через триггеры или расширение) для медицинской прослеживаемости.
- **Партиционирование** `appointments`/`slots` по времени при росте объёмов.
- **История статусов** записи отдельной таблицей (кто, когда, из какого в какой статус).
- **Интеграция с МИС/ЕГИСЗ / FHIR**: маппинг `patients/appointments` на ресурсы `Patient`/`Appointment` — задача отображения, не переписывания.
- **Резервирование слота (hold)**: статус `held` + TTL для сценария «пациент подтверждает запись N минут».

## 7. Как запустить

```bash
createdb clinic
psql -d clinic -v ON_ERROR_STOP=1 -f init_schema.sql
# примеры/сценарии:
psql -d clinic -f init_data.sql
```

Схема применяется идемпотентно в части ролей и типов (`IF NOT EXISTS` / перехват `duplicate_object`); таблицы создаются с нуля.
